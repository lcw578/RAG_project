# 工程发现与部署要点

## 1. llama.cpp HTTP keep-alive 缺陷（隔次 404）

**现象**：复用同一 HTTP 连接调用 llama-server（b11429）时，请求会"隔次"返回 `404 File Not Found`，100% 可复现且严格交替（OK / 404 / OK / 404…）。

**对照实验**：

| 场景 | 结果 |
|---|---|
| 持久连接（客户端连接复用） | OK/404 严格交替，10/10 复现 |
| 每题新建连接 | **10/10 全部 OK** |

**工程处理**：客户端强制**每题新建连接**（`qa_llama*.py` 中 `[ADAPTED]` 已固化，本机建连毫秒级，无性能影响）。

## 2. 思考模式（thinking）A/B 实验：明确否决

**实验设计**：同一批 300 题（chunk 00），仅切换 `enable_thinking`，`max_tokens=2048`。

| 题型 | 思考关 | 思考开 |
|---|---|---|
| comparison | 43.0% | 2.0% |
| inference | 96.8% | 12.8% |
| null | 57.5% | **72.5%**（唯一提升） |
| temporal | 30.3% | 0.0% |
| **总体** | **59.0%** | **14.3%** |

**根因**：思考开时 **70%（210/300）的题输出 content 为空**——2048 token 预算被思维链耗尽，最终答案未生成；单题耗时 30s（关思考 0.56s，48 倍）。
**结论**：9B 量级模型的思维链深度撑不起本任务的证据量；正式配置**默认关闭思考**（与官方默认一致）。唯一亮点是 null 类提升（识别"答不了"），因无法在不引入标注的情况下做题型路由而未采用。

## 3. 证据的"时间隐形"现象

**统计**：全量 26586 段证据 chunk 中，**98.2%（26099 段）的正文不含自身发布日期**（新闻正文使用相对时间："本周三""上个月"）。
**含义**：对 temporal 类问题（时间顺序/变化判断），模型在做题时**看不到证据的发布时间**，时间线无从建立。
**对策**：日期标注注入（`[Published: YYYY-MM-DD]` 前缀，数据来自语料 `published_at` 元数据）+ prompt 时间线引导 → temporal 类 38.8 → 57.6（+18.8pp）。

## 4. 其他部署要点（踩坑记录）

| 项 | 要点 |
|---|---|
| PyTorch | conda 环境需 `setuptools<81`（llama-index 0.9.x 依赖 pkg_resources）；CUDA 版 torch 走 SJTU 镜像（清华 pytorch-wheels 已 404） |
| llama.cpp 服务 | 端口避开常用（用 18080）；`--jinja` 启用 chat 模板；`chat_template_kwargs: {"enable_thinking": false}` 关闭思考 |
| 模型下载 | `hf` CLI 新版默认 Xet 协议，部分镜像 401 → `HF_HUB_DISABLE_XET=1` |
| GPU 重排 | FlagEmbedding 在推理时自动选择 CUDA（无需显式指定 devices）；fp32 显存占用约 2.3GB |
| 大文件处理 | 前台大内存操作（多文件 JSON 合并分析）建议放入后台任务运行，避免被行级限制中断 |
